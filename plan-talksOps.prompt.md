## Plan: TalksOps Implementation

Build TalksOps as a .NET 10 solution with a Blazor Server BFF, Azure Functions isolated-worker API, Azure Tables persistence, and Bicep/AZD provisioning. Preserve the requested per-user/event partitioning, keep storage and REST contracts in separate projects, and implement Microsoft personal-account sign-in in application code (not App Service Easy Auth).

**Steps**
1. Establish the solution skeleton: `TalksOps.sln`, root `azure.yaml`, shared build settings, and `src/` projects for `TalksOps.Core`, `TalksOps.ApiClient` (DTOs, client interface and implementation), `TalksOps.Storage`, `TalksOps.Functions`, and `TalksOps.Web`; create focused `tests/` projects. Target `net10.0`, enable nullable reference types, and use English identifiers and content.
2. Define domain types and contracts in Core: `Event`, `SessionProposal`, proposal status enum (`Submitted`, `Accepted`, `Rejected`, `Cancelled`), validation/business rules, current-user and persistence/service interfaces. Define REST DTOs and `ITalksOpsApiClient` in ApiClient; implement the typed HTTP client there. Do not leak Azure Table entity types across project boundaries.
3. Implement persistence in Storage using Azure Tables SDK and managed identity in Azure. Map events to entities partitioned by authenticated user ID and keyed by event GUID; map proposals to entities partitioned by event GUID, keyed by proposal GUID, and retain owner ID for ownership checks. Serialize the costs dictionary into a supported table property. Filter event searches within the caller's partition; support year/name/location and pagination as appropriate. A session can be delete from the storage. A proposal with "Cancelled" status means that the proposal is in the storage but the speaker withdrew from the event.
4. Implement Functions endpoints for event CRUD/search, proposal CRUD/status transitions, and calendar data. Validate inputs and ownership on every operation; derive the payload `userId` from the authenticated Blazor Server principal (`sub`) in a scoped user context, never from editable form input. Register Storage/Core services through DI. The Blazor Server client calls Functions server-to-server; keep the Function key in server configuration/Key Vault and never expose it to browser code. Document the residual risk that possession of the shared key allows a caller to assert a different payload user ID; do not treat the key as per-user authentication.
5. Implement Web with code-based OpenID Connect using Microsoft.Identity.Web and a Microsoft personal-account-only app registration (`PersonalMicrosoftAccount` audience / consumer authority). Use authenticated server-side Blazor pages for event search (default current year), add/edit/delete with confirmation, proposal add/edit/status/cancel, and an annual calendar. Calendar status colors are computed per event with a documented precedence when proposals have mixed states. Apply authorization to all application pages and handle sign-in/out and API errors. If the application run locally, bypass the authentication using a fake account make possible to run locally without configuring any identity and app registration on Azure.
6. Provision with AZD and Bicep: root `infra/main.bicep`; cohesive `monitoring`, `frontend`, `backend`, and `storage` modules plus an `identity` provisioning path; include `infra/abbreviations.json`. Provision App Service, Function App, storage account and tables in table service, Log Analytics/Application Insights, settings/endpoints, and role assignments. Give the Function App managed identity the least-privilege Table Data role for application data and only the additional roles required by Functions host storage. Use Bicep parameters/outputs for nonsecret settings only. Provision the Entra app registration for personal accounts and configure the App Service callback/credentials without Easy Auth; validate the Graph permissions, deployment scope, and AZD orchestration in an early infrastructure spike because tenant-level app registration provisioning has different scope and permission requirements from resource-group resources. Keep the Function key out of IaC outputs; document a secure Key Vault/bootstrap path for making it available to the server-side web app.
7. Add documentation in English: root README architecture Mermaid and usage/prerequisites; README in every C# project describing its purpose, features, classes, a Mermaid class diagram; `infra/README.md` describing modules and provisioning via Azure CLI and AZD. Update `.gitignore` for `.azure/`, secrets, local settings, build outputs, and generated infrastructure artifacts.
8. Verify locally and in a disposable Azure environment: build all `net10.0` projects; run unit tests for validation, ownership, status transitions, and calendar classification; run Storage/Functions integration tests using an isolated development account or emulator where supported; validate Bicep, AZD packaging, auth redirects, CRUD/search/cascade behavior, calendar rendering, managed-identity RBAC, and monitoring. Do not run provisioning/deployment without explicit environment/subscription/tenant/region confirmation.

**Decisions**
- Authentication audience: personal Microsoft accounts only, as selected by the user.
- API access: server-side Blazor calls Functions with a Function key; user ID is derived from the authenticated `sub` claim and included in each request payload. The key remains server-side. A compromised shared key still permits identity spoofing unless API token validation or another stronger binding is added.
- Proposal removal means transition to `Cancelled`, preserving the record, consistent with the supplied data model.
- Scope includes implementation, deployment documentation, and focused tests. No deployment is authorized by this plan; production CI/CD, extra identity providers, and unrelated features are excluded.
- All solution labels, comments, identifiers, and documentation are in English.
